# Vercel + Neon deployment

The production project is `returntail` at https://returntail.vercel.app. Deployment verification results are recorded in BUILD_STATUS.md; a successful build alone does not establish runtime or wallet readiness.

1. Provision PostgreSQL on Neon; use the intended database/pooler URL with required TLS settings. Keep the URL only in secure environment configuration.
2. Set `AUTH_SECRET` (random >=32 characters), canonical `NEXT_PUBLIC_APP_URL`, `BCH_NETWORK`, `DATABASE_URL`, and `CRON_SECRET`. For a mainnet release set mainnet deliberately at build and runtime. Default primary bch.imaginary.cash / witness bch0.kister.net were checked; optional host/port overrides must be independent and serve the configured chain.
3. Apply `npm run db:migrate` from a controlled environment. The runner acquires an advisory lock, checks the migration checksum, and wraps DDL/recording in a transaction. It refuses a modified applied migration. Create a new migration for future schema changes rather than editing applied SQL.
4. Keep the existing public GitHub repository connected to Vercel. `vercel.json` explicitly selects `nextjs` and `npm run vercel-build`; the framework must not be left as Other, which serves `public` and drops application routes. The separate video package is excluded from app TypeScript/build dependencies.
5. The production build runs the atomic, checksum-verified migration before `next build --webpack`. A migration failure stops deployment. Preview/local builds skip automatic migrations. Never point fixture tests at the production database. Run `npm run smoke -- https://returntail.vercel.app` after deployment; it checks public pages/assets, DB readiness and unauthenticated workspace rejection without creating accounts/orders or sending money.
6. Verify merchant login/session cookies over HTTPS, customer private capability flow, actual wallet relay and network choice, genuine mainnet payment/refund and receipt in the deployment and wallet checklist. Localhost production-mode checks are not hosted verification.
7. Confirm authenticated cron `/api/jobs/reconcile` accepts only `Authorization: Bearer CRON_SECRET`. Free Vercel cron is scheduled daily. The UI also reconciles pending signed attempts periodically; no real-time SLA is promised. Providers can fail; unknown attempts remain reserved.
   With the same authorization, `GET /api/jobs/network` checks outbound TLS, configured chain checkpoints, and primary/witness agreement from the deployed runtime. It performs no transfer or address query. Never place CRON_SECRET in a URL, browser code, screenshots or committed command examples. Unauthenticated access must return 401.
8. Supply real Widget Factory and token-compatible donation settings. Optionally set `PUBLIC_PROOF_REFUND_ID` to the actual confirmed mainnet refund; `/evidence` only surfaces it after persisted merkle/witness confirmation evidence meets the gate. Do not put a test fixture into production evidence.

Operational responsibilities: database backup/retention, secret rotation plan, public-provider monitoring, scheduler, private support channel and account-recovery policy. Logs intentionally contain normalized event codes rather than raw transactions, public keys, customer reasons or credentials. Account email is not yet independently verified; no password-recovery mailer is implemented. These limits are disclosed before general availability.

No automatic migration runs on each serverless request. No debug seed endpoint is deployed. Fixtures are test-source-only and browser fixture tests refuse non-local URLs.
